// systemverilog · zig · c++ · verilator

RTL Verification
Framework

Complete · Checking hardware against an independent reference model

The idea

Hardware bugs are expensive in a way software bugs aren't — once a chip design is fabricated, there's no patching it. Verification is the practice of proving a hardware design is correct before that happens, and real verification means checking a design against an independent definition of "correct" — not just reading the RTL and trusting it does what it looks like it does.

This project is a framework that automatically checks SystemVerilog hardware designs against independently-written Zig reference models, running both side by side and comparing their behavior cycle by cycle.

How the pipeline works

Three independent pieces have to agree for a test to pass:

The RTL design — the actual hardware module, written in SystemVerilog, the same language a real ASIC or FPGA design would use.

The reference model — a completely separate implementation of the same expected behavior, written in Zig. This is the "golden" model: if the RTL and the reference model ever disagree, the RTL is presumed wrong, not the other way around.

The testbench — a C++ program that drives both the RTL and the reference model with identical inputs, every clock cycle, and compares their outputs directly. Verilator compiles the SystemVerilog into C++ so it can run in the same process as the Zig model, linked together through a small C-compatible interface (*_init(), *_tick(), *_set_*(), *_get_*()).

Two modules are verified this way so far: an 8-bit counter with synchronous enable and async reset, and a parameterized synchronous FIFO with full/empty status flags.

Beyond just checking the data

For the FIFO specifically, matching output values isn't the whole story — a FIFO can return the right data at the wrong time and still be broken. The testbench includes a dedicated latency checker that tracks every value from the cycle it's written to the cycle it's read back out, recording minimum, maximum, and average write-to-read latency, and flagging a violation if anything takes longer than it should.

Checking that the right data eventually comes out isn't the same as checking that the hardware behaves correctly — a design can be functionally right and still be wrong in time. Catching that class of bug requires verifying timing as a first-class property, not just correctness.
